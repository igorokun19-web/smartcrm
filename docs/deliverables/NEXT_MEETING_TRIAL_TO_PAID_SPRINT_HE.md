# ספרינט סגור לפגישה הבאה: Trial חודש ראשון חינם -> חיוב מסודר ובטוח

## מטרה עסקית
להעלות לאוויר מודל מסחרי שבו כל משתמש חדש מקבל חודש ראשון חינם, ובסיום התקופה מתבצע מעבר מסודר לתשלום, עם שקיפות מלאה למשתמש ובטיחות תפעולית.

## תוצאה צפויה בסוף הפגישה
1. לוגיקה עסקית מלאה ומוגדרת (מדיניות Trial, תזכורות, מעבר לתשלום).
2. הטמעה מערכתית מקצה לקצה ב-Backend + Frontend + DB.
3. מסך ניהול מנוי ברור למשתמש.
4. נתיב חיוב מאובטח ומבוקר, כולל Fail-safe.
5. בדיקות קבלה ו-Launch Checklist מוכנים להרצה.

## החלטות עסקיות שנקבע בתחילת הפגישה (15 דקות)
1. אורך Trial: 30 יום.
2. מדיניות סיום Trial:
- אפשרות A: חסימה חלקית עד חידוש מנוי.
- אפשרות B: מצב קריאה בלבד עד תשלום.
3. תמחור התחלתי:
- תכנית בסיס.
- תכנית פרו.
4. מדיניות חריגים:
- הארכת ניסיון אוטומטית אם לא הושג ערך מינימלי.
- כללי זיכוי או ביטול.

## הגדרת "עובד כמו שצריך" (Value Gate)
המערכת תחשב ערך שימוש מינימלי במהלך ה-Trial. דוגמה להגדרה התחלתית:
1. לפחות 5 לידים חדשים.
2. לפחות 3 משימות שנוהלו.
3. לפחות 1 מסמך כספי (חשבונית או הצעת מחיר).

אם המשתמש לא מגיע לסף, ניתן להחיל הארכה של 7 ימים במקום חיוב מיידי.

## היקף טכני לפיתוח בספרינט

### Backend
1. ישויות/שדות מנוי:
- plan: free_trial, basic, pro
- trial_started_at
- trial_ends_at
- subscription_status: trialing, active, past_due, canceled
- billing_customer_id
- billing_subscription_id
2. Middleware הרשאות לפי סטטוס מנוי.
3. Endpoints חדשים:
- GET /api/billing/status
- POST /api/billing/start-checkout
- POST /api/billing/webhook
- POST /api/billing/cancel
4. Cron/Job יומי:
- עדכון סטטוסים ל-Trial שפג.
- הפעלת תזכורות ימים 25/28/30.
5. Audit Log על אירועי חיוב קריטיים.

### Frontend
1. מסך Billing חדש:
- סטטוס Trial.
- ימים שנותרו.
- תאריך חיוב הבא.
- כפתור שדרוג תכנית.
2. Banner בתוך האפליקציה:
- הודעות לפני סיום Trial.
3. Feature gating:
- הודעת שדרוג בפעולות נעולות.
4. מסך הצלחה/כישלון תשלום.

### Database
1. Migration לטבלת users או subscriptions עם השדות החדשים.
2. אינדקסים על subscription_status ו-trial_ends_at.
3. טבלת billing_events לשחזור ואבחון.

## שילוב ספק סליקה (מומלץ)
להתחיל עם Stripe בגלל יציבות, תיעוד ו-Webhooks ברורים.

נדרש:
1. יצירת Checkout Session.
2. קליטת webhook חתום:
- checkout.session.completed
- invoice.payment_succeeded
- invoice.payment_failed
- customer.subscription.deleted
3. עדכון סטטוס משתמש לפי אירוע.

## תכנית עבודה בפגישה (ספרינט סגור)
1. בלוק 1 - אפיון והחלטות (30 דק).
2. בלוק 2 - מודל נתונים ומיגרציה (45 דק).
3. בלוק 3 - Backend API + Webhook + Jobs (90 דק).
4. בלוק 4 - Frontend Billing UI + Gating (90 דק).
5. בלוק 5 - QA תרחישים מקצה לקצה (45 דק).
6. בלוק 6 - Go/No-Go + תכנית השקה (20 דק).

## תרחישי QA מחייבים
1. משתמש חדש מקבל Trial אוטומטי (30 יום).
2. יום 25 נשלחת תזכורת ראשונה.
3. יום 28 נשלחת תזכורת שנייה.
4. יום 30 ללא תשלום:
- שינוי סטטוס לפי המדיניות שנבחרה.
5. תשלום הצליח:
- מעבר ל-active.
- פתיחת פיצ'רים.
6. תשלום נכשל:
- מעבר ל-past_due.
- הודעה למשתמש + נתיב תיקון תשלום.
7. ביטול מנוי:
- מעבר ל-canceled במועד הנכון.

## דרישות אבטחה וציות
1. לא לשמור פרטי כרטיס במערכת.
2. אימות חתימת Webhook.
3. Idempotency לכל אירוע billing נכנס.
4. Rate limiting ל-endpoints פיננסיים.
5. לוגים בלי מידע רגיש.

## Launch Checklist
1. Variables מוגדרים בסביבת Production.
2. Webhook endpoint פעיל ומאומת.
3. בדיקות sandbox עברו מקצה לקצה.
4. Feature flag להפעלה מדורגת.
5. דשבורד ניטור המרות Trial -> Paid.
6. מסמך Runbook לטיפול בכשלי חיוב.

## KPI לשבועיים ראשונים
1. Conversion Trial -> Paid.
2. אחוז משתמשים שמגיעים ל-Value Gate.
3. Churn ב-14 יום לאחר חיוב ראשון.
4. Payment failure rate.
5. זמן ממוצע ל-First Value.

## תוצרי סיום הפגישה
1. קוד מוטמע ועובד בסביבת פיתוח.
2. מסכי Billing פעילים.
3. בדיקות QA מתועדות עם Pass/Fail.
4. תכנית עלייה לאוויר עם תאריך יעד.
5. רשימת פעולות קצרה לפוליש שלא חוסמת חיוב.
